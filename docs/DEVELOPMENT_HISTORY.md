# MapMaker 개발 과정과 개선 기록

이 문서는 초기 생성 방식의 실험부터 현재 객체별 장면 생성과 배치 보정까지, **시도한 방식 → 관찰한 문제 → 변경 내용 → 확인된 결과** 순서로 정리한다. 현재 구현의 구체적인 데이터 흐름과 수식은 [상세 구현](IMPLEMENTATION.md)에 있다.

작성 기준은 2026-09-29다. 과거 단계는 Git에 보존된 당시 문서, 현재 보정은 저장소의 검증 보고서를 근거로 한다. 목표와 선택 이유는 사용자에게 확인했으며, 보고서로 확인한 실험과 사용자 회고를 구분해 표시한다. 아래 결과를 이 문서 작성 중 재실행한 것은 아니다. 기존 실행 환경과 일부 원본 산출물은 현재 checkout에 없으므로, 과거 기록을 현재 재현 완료 결과로 해석하지 않는다.

## 1. 접근 방식의 변화

초기 목표는 사진에 보이는 방뿐 아니라 **주변까지 포함한 온전한 3D 장면을 복원하고, 구성 객체를 편집할 수 있게 만드는 것**이었다. Diffusion360·InSpace 실험에서는 방 전체 구조와 가구 배치를 함께 생성하는 것, 원본에 보이지 않는 주변 공간까지 만드는 것 모두를 목표로 했다. 이 개발 의도는 문서 작성 과정에서 사용자가 확인한 내용이다.

여기서 주변 공간의 생성은 실제로 관측하지 못한 영역을 추정하는 작업이다. 초기 목표의 ‘온전한 장면 복원’과 실험으로 입증한 ‘실제 숨은 공간의 정확한 복원’은 구분한다.

**초기 목표는 현재도 유지한다. 이번 1차 구현 범위는 객체별 3D 생성·장면 조립·배치 보정·웹 확인까지다.** 주변 공간 전체 복원과 객체 위치·회전 등을 바꾸는 편집 UI는 아직 구현하지 않았다. 현재 범위를 초기 목표의 완전한 달성이나 목표 자체의 폐기로 설명하지 않는다.

| 단계 | 시도한 방식 | 기록에서 확인되는 성과 | 남은 문제 |
|---|---|---|---|
| 초기 객체 중심 생성 | MoGe 깊이, GEN3C 생성 시점, RAM++·SAM3, Hunyuan 메시를 연결 | 객체 메시와 원본 시점의 장면 구성 | 생성 측면의 신뢰성, 형상 오류, 배치와 가림 |
| 원본 시점 보완 | 깊이 기반 관측 표면, 배경 보완, 렌더링·배치 수정 | 원본 시점의 미피복 영역과 실루엣 대응 개선 | 뒷면을 포함한 완전한 객체 형상 복원은 아님 |
| 공간 전체 생성 실험 | Diffusion360 파노라마 → InSpace | 공식 예제에서 방과 독립 asset 생성 확인 | 자체 거실 입력에서 주요 가구 소실 |
| SAM3D 기반 통합 | 원본 이미지·마스크에서 메시와 pose를 얻어 독립 노드로 조립 | 자동 객체 추출, GLB, 웹 뷰어까지 연결 | 기울기·부유·접촉 문제 |
| 실행 환경 확장 | Windows 서버 + RunPod GPU + S3 | 원격 생성과 결과 확인·다운로드 | 초기 로딩, 비용, 저장 용량, 중단 복구 제약 |
| 배치 보정 v1~v4 | 높이 보정 → 공통 정렬 → 가구 직립 → 전체 객체 직립 | 정렬·지정 가구 접지와 비교 검증 | 의미적 자세·소품 지지·충돌은 미해결 |

서로 다른 단계는 목표와 평가 조건도 달랐다. 이를 하나의 정확도 그래프로 합치거나, 뒤 단계가 모든 측면에서 앞 단계보다 우수하다고 결론 내리지는 않는다.

## 2. 초기 경로: 추가 시점과 객체별 메시 생성

2026-09-22 기록의 초기 경로는 다음과 같다. Hunyuan은 이때 분리된 객체 이미지에서 메시를 만드는 단계에 사용되었으며 현재 파이프라인에는 사용하지 않는다.

```text
원본 이미지 → MoGe 깊이·카메라 추정 → GEN3C 추가 시점 생성
→ RAM++ 후보 → SAM3 객체 분리 → 객체별 뷰 선별
→ Hunyuan3D 메시 → 원본 공간에 배치 → scene.glb
```

### 2.1 카메라가 회전한 것과 실제 측면이 생성된 것은 달랐다

초기 짧은 GEN3C 궤도는 약 17도 사선 관측에 머물렀다. 이후 좌우 90도 원호 궤도로 바꾸고 방향마다 121프레임을 생성했다. 카메라 행렬에서는 0→90도 이동이 확인되었지만, 생성 영상의 소파·TV·수납장 등이 실제 측면으로 충분히 돌아가지 않거나 주변 세부가 달라지는 문제가 기록되어 있다.

이 때문에 카메라 각도만으로 프레임을 Hunyuan의 측면 입력으로 인정하지 않았다. 시각 확인을 통과한 객체와 충분한 카메라 각도가 함께 있는 경우에만 측면으로 사용하도록 제한했다. 당시 검토 영상은 측면 승인을 받지 못했다.

확인한 문제는 **추가 이미지가 존재해도 서로 일관된 다중 시점 관측이라고 볼 수 없다는 것**이다. 모델이 생성한 시점은 실제 촬영한 시점과 같은 기하학적 근거가 아니다.

근거: `3ed4b1d:README.md`, `90eb0ac:README.md`.

### 2.2 형상·배경·가림을 보완한 단계

후속 거실 검증에서는 소파·테이블의 생성 기하를 채택하고, 형상이 맞지 않은 식물은 원본 깊이의 관측 표면으로 대체했다. 겹치는 쿠션과 중복 구조물을 통합하고, 객체 마스크를 제거한 자리에 생기는 배경 구멍도 보완했다.

렌더링은 평균 깊이 순서의 덧칠에서 픽셀별 Z-buffer와 원근 보정 텍스처 보간으로 변경했다. 배치는 좌표축 변환, 회전, 축별 크기, 위치와 원본 깊이의 가림 관계를 함께 다뤘다. 한 문제를 메시 생성만으로 해결하려 하지 않고, 형상·배경·렌더·배치를 구분하여 수정한 단계다.

| 동일 원본 시점 비교 | 이전 | 보완 후 |
|---|---:|---:|
| 메시가 없는 픽셀 비율 | 13.802% | 0.000% |
| 대응 객체 가시 영역 IoU 평균 | 0.369 | 0.991 |
| 소파 가시 영역 IoU | 0.753 | 0.968 |
| 테이블 가시 영역 IoU | 0.717 | 0.897 |

위 수치는 640×427에서 같은 새 원본 마스크·Z-buffer·카메라를 사용한 당시 보고서의 값이다. 관측 표면은 원본 깊이와 마스크를 재투영하므로 높은 일치도가 나올 수 있다. **0.991을 3D 복원 정확도 99.1%로 표현하면 안 된다.** 원본 시점의 대응이 좋아졌다는 결과이며 보이지 않는 뒷면의 정확도를 검증한 것은 아니다.

사용자가 확인한 당시의 핵심 불만은 **객체 모양이 부자연스럽고 전체 배치도 어색했다는 점**이다. 원본 시점의 수치가 개선되더라도 원하는 온전한 장면과 객체 형상을 얻는 문제는 남아 있었다. 다음 실험에서는 방 구조와 가구 배치를 함께 생성하고 주변 공간도 확장하는 접근을 시험했다.

근거: `522b682:docs/living_room_validation.md`.

## 3. Diffusion360 → InSpace 실험

이 단계에서는 사진을 파노라마로 확장한 뒤 방과 가구를 생성하는 경로를 시험했다.

```text
거실 사진 → Diffusion360 파노라마 → 6방향 perspective 이미지
→ InSpace coarse scene → layout·객체 geometry·texture
```

당시 문서는 Hunyuan single/multi-view와 FLUX Fill 기반 보완에서 안정적인 geometry 개선을 확인하지 못해 공간 전체를 먼저 생성하는 실험을 진행했다고 설명한다. FLUX Fill의 개별 실험 조건·수치까지 이 기록에 충분히 남아 있는 것은 아니므로, Hunyuan과의 정량 비교나 상세한 실패 원인은 추가로 단정하지 않는다.

### 3.1 자체 입력과 공식 예제를 나눠 확인

사용자 회고에 따르면 해당 저장소가 제공한 이미지에서는 작동했지만, **인터넷에서 구한 실제 파노라마와 Diffusion360 등의 모델로 생성한 파노라마에서는 정상적인 장면을 얻지 못했다.** 제공 예제 밖의 입력에서 기대한 결과를 얻지 못한 경험이 다음 접근을 검토한 배경이었다. 여기서 ‘정상 생성되지 않았다’는 사용자 관찰이며, 실제 파노라마 실험별 입력 수·설정·정량 지표는 이번에 확인한 기록으로 확정하지 않았다.

아래의 구체적인 결과는 그중 문서가 남아 있는 Diffusion360 거실 실험과 공식 침실 대조를 설명한다.

자체 거실 사진으로 만든 파노라마에서는 소파와 테이블이 대략 보였지만, InSpace 결과에는 식별 가능한 독립 소파·테이블이 나오지 않았다. bbox 후보 5개 중 4개가 최소 decode 크기 기준에 미달했고 독립 asset은 1개만 남았다. 이 결과는 당시 baseline으로 채택하지 않았다.

동일 환경의 공식 침실 예제에서는 방과 독립 asset 5개가 생성되었다. 따라서 모델이나 설치 환경이 전혀 작동하지 않는 문제와, 자체 입력에서 기대한 결과를 얻지 못한 문제를 구분할 수 있었다. 공식 예제에도 침대에 조명 조각이 섞이거나 협탁 상판이 빠지는 문제가 남았다.

파노라마에 새로 나타난 복도·문 등은 생성된 확장 영역이다. 실제로 보이지 않던 공간을 확인해 복원한 결과로 표현하지 않는다. 원본 식물의 대응 실패는 파노라마 단계에서도 관찰되었다.

### 3.2 원인을 분리하기 위한 대조 실험

공식 예제에서 공간 prior 사용 여부(PSG)와 camera 조건을 나누어 확인했다. 초기 대조에서는 encoder의 무작위 view embedding 때문에 영상 conditioning도 달라졌고, 이후에는 저장한 같은 RGB conditioning tensor를 사용했다.

| 공식 침실 조건 | 정답 coarse voxel과의 IoU |
|---|---:|
| PSG-on, 제공 camera | 약 0.8001 |
| PSG-off, 제공 camera | 약 0.9834 |
| PSG-off, camera만 원점으로 변경 | 약 0.0452 |

이 수치는 해당 예제·seed·좌표계의 coarse voxel 비교다. 최종 텍스처 메시나 객체 분리 품질 점수가 아니다. PSG on/off는 초기 latent와 sampling 시간 구간도 달라지는 toggle이므로 prior 하나만 독립적으로 제거한 실험으로 해석하지 않는다.

확인된 것은 camera와 좌표 정규화 조건이 결과에 큰 영향을 줄 수 있다는 점이다. 자체 거실의 실패 원인이 camera 하나라고 확정되지는 않았고, PSG가 항상 불필요하다거나 파노라마 방식 전체가 실패한다고 일반화할 수 없다.

근거: `0e213d5:docs/inspace_current_issues_2026-09-24.md`.

## 4. SAM3D 기반의 자동 파이프라인으로 통합

파노라마 기반 접근에서 제공 예제 외 입력의 생성 문제를 겪은 뒤, 현재는 원본 이미지와 객체별 마스크에서 생성하는 SAM3D 경로를 사용한다. 이번 단계의 목표는 유지 중인 전체 장면 복원·편집 목표를 향해, 우선 객체별 생성이 동작하는 시스템을 완성하는 것이다. SAM3D 선택을 모든 후보 모델에 대한 정량적 우위가 입증된 결과로 설명하지 않는다.

전환 조사 당시에는 SAM3D로 생성에 성공한 객체별 GLB·pose·Gaussian 결과가 있었지만, 실험용 객체 목록은 사람이 정한 고정 목록이었다. 합성 장면 GLB와 업로드·생성·표시 전환을 갖춘 웹 앱도 별도로 구현해야 했다.

통합 단계에서는 다음을 바꿨다.

- 객체 목록을 이미지별 수기 지정에서 RAM++의 실제 추론과 공통 필터로 바꿨다.
- SAM3의 원본 해상도 마스크를 객체별 SAM3D 추론에 연결했다.
- 공식 pose와 GLB 내보내기 축 변환을 맞춰 독립 객체 노드의 `scene.glb`를 만들었다.
- 실행별 중간 산출물·오류를 저장하고 웹에서 생성·탐색·다운로드하도록 연결했다.

환경 재현도 별도 문제였다. 기존 성공 Python 환경이 임시 경로에 있다가 사라져, 모델 파일은 남아 있어도 동일 실행을 바로 재현할 수 없었다. 이후 영구 SAM3D 환경과 DINOv2 cache를 복구하고, 고정 소파 마스크·seed로 pose와 메시 크기 차이를 확인했다.

당시 자동 거실 실행에서는 6개 객체가 생성되었고, 기존 수기 기준 5개 객체에 해당하는 결과를 모두 얻었다. 사과 입력에서는 2개 객체 생성과 실제 브라우저 업로드·생성·표시 전환·다운로드 검사가 기록되어 있다. 이는 자동 경로의 동작 근거이며 이전 모델들보다 모든 입력에서 품질이 우수하다는 비교 실험은 아니다.

근거: `e7c4904:docs/sam3d_project_investigation.md`, `e7c4904:docs/sam3d_project_validation.md`.

## 5. 원격 GPU와 사용 가능한 앱으로 확장

Linux GPU 환경의 생성 기능을 Windows에서도 사용할 수 있도록 로컬 서버와 RunPod worker를 분리하고 S3로 입력·결과를 전송했다. 진행 상태, 작업 ID, 입력·결과 해시를 기록하고 브라우저에서 기존 실행을 다시 열 수 있게 했다.

이 과정에서는 모델 정확도와 다른 종류의 문제가 나타났다. 비전 환경의 Python symlink를 실제 경로로 풀면 의도한 가상환경이 사라지는 문제, worker의 빌드 캐시, S3 저장 용량 초과, 서버 재시작 중 미완료 작업 등이 각각 코드·운영 처리의 대상이었다.

이 단계의 개선은 **같은 생성 기능을 실행하고 결과를 확인하는 안정성**에 해당한다. 원격화 자체로 메시 품질이 좋아졌다는 의미는 아니다. 현재 전송·실패 정책은 [상세 구현 6절](IMPLEMENTATION.md#6-원격-gpu-실행과-결과-수신), 당시 기록은 [프로젝트 상태](../PROJECT_CURRENT_STATE.md)와 [RunPod 검증 JSON](runpod_serverless_validation.json)에 있다.

## 6. 배치 보정 v1~v4

### 6.1 출발점: 좌표 변환이 맞아도 가구가 바닥에 놓이지 않았다

공식 pose와 GLB 변환의 수치 검사를 통과했어도 가구의 최저 높이가 서로 달랐고 공통 바닥 제약이 없었다. 당시 조사에서 축 변환이나 pivot 처리 오류가 입증된 것은 아니다. 모델의 추정 결과를 올바르게 옮기는 것과 사용하기 자연스러운 장면을 만드는 것은 별개의 문제였다.

| 단계 | 변경 내용 | 확인한 개선 | 남은 문제·변경된 성질 |
|---|---|---|---|
| v1 | 지정 가구 최저점의 중앙값으로 바닥 추정, 개별 Y 이동, 제한적 소품 추종 | 일부 가구의 높이 불일치 제거, 바닥 표시 | 공통·개별 기울기를 유지 |
| v2 | 모든 객체의 평균 위쪽 방향으로 공통 회전, 전체 최저점 Y=0 | 장면의 공통 기울기 감소, 상대 변환 보존 | 개별 가구의 부유·자세 차이 유지; v1 소품 추종 제거 |
| v3 | 공통 정렬 후 지정 가구를 각 root 중심으로 직립·접지 | 지정 가구의 축 정렬과 접지 | 소품은 따라가지 않아 접촉이 깨질 수 있음 |
| v4 | 개별 직립을 모든 객체로 확대, 접지는 지정 가구에만 적용 | 비가구의 로컬 축 정렬도 일관되게 적용 | 실제 의미적 위쪽·지지 관계·충돌은 여전히 미해결 |

v1의 기능을 모두 유지하면서 추가한 누적 구조가 아니다. v2에서는 개별 높이 보정과 소품 추종을 제거했고, v3·v4에서는 다른 개별 보정 규칙을 도입했다.

### 6.2 v1: 높이 차이를 먼저 보정

대상 가구의 최저 높이 중앙값을 바닥 높이로 삼고 Y 위치를 맞췄다. 객체 높이의 50%를 넘는 이동은 제외하고, 지지 가구가 하나로 판단되는 제한된 소품만 같은 높이 이동을 따르게 했다. 회전·크기·XZ는 유지했다.

저장된 거실·식당·침실의 30개 객체 중 선정 가구 16개를 평가했고, 부유 7→0, 바닥 관통 7→0이 기록되었다. 기준은 실제 바닥 정답이 아니라 추정한 동일 바닥과 허용오차다. 식당의 큰 AABB 겹침 쌍은 6→7로 늘었으므로 충돌까지 해결한 결과가 아니다.

근거: [v1 배치 검증](placement_validation.md).

### 6.3 v2: 장면 전체의 기울기 정렬

각 객체의 로컬 +Y를 조립 좌표로 옮긴 뒤 정규화하여 동일 가중치로 평균했다. 그 평균을 월드 +Y로 회전시키고, 모든 객체에 같은 이동을 적용해 전체 최저점을 Y=0에 맞췄다.

22개 장면·120개 객체의 수치 검사에서 상대 행렬 최대 오차는 `1.78e-15`, 전체 최저 Y의 최대 절댓값은 `2.22e-16`이었다. 3개 장면은 새 GLB와 뷰어까지 확인했고 나머지 19개는 메모리상 수치 검사였다. 전부 GPU 재추론 없이 저장 결과를 사용했다.

| 기존 높이 보정 v1 | 공통 정렬 v2 |
|---|---|
| ![v1 식탁과 책장](assets/global_alignment/a738b5f0_before.png) | ![v2 식탁과 책장](assets/global_alignment/a738b5f0_after.png) |

책장·식탁·의자의 공통 방향은 달라졌지만 바닥 위로 뜬 가구가 남았다. 분리된 작은 조각까지 포함한 전체 범위로 바닥을 생성하여 바닥이 넓어졌다. 이 비교는 각 결과의 자동 fit 카메라를 사용하므로 배율과 구도가 동일하지 않다.

근거: [v2 공통 정렬 검증](GLOBAL_ALIGNMENT_VALIDATION.md).

### 6.4 v3: 가구마다 직립·접지

공통 정렬로 해결되지 않은 가구별 기울기와 높이를 다뤘다. 지정 가구를 자기 root 중심으로 회전시키고 실제 메시 최저점을 Y=0에 맞췄다.

22개 장면에서 지정 가구 46개를 검사했으며 공통 정렬 직후의 부유 가구 39개가 개별 보정 후 0개가 되었다. 대상 최저점의 최대 절댓값은 `1.39e-17` scene units였다. 이 값은 대상 가구의 접지 규칙이 수치적으로 지켜졌다는 의미이며 모든 물체의 부유가 사라졌다는 뜻은 아니다.

| 공통 정렬 v2 | 가구 개별 정렬 v3 |
|---|---|
| ![v2 가구 부유](assets/global_alignment/a738b5f0_after.png) | ![v3 가구 접지](assets/individual_alignment/a738b5f0_after.png) |

가구는 더 똑바로 서고 바닥에 닿았지만 식물·소품은 따라 이동하지 않았다. 이 비교도 자동 fit 카메라이므로 완전히 같은 구도는 아니다. v2와 마찬가지로 3개 대표 장면만 새 GLB·뷰어까지 검증했고 나머지는 수치 검사다.

근거: [v3 개별 정렬 검증](INDIVIDUAL_ALIGNMENT_VALIDATION.md).

### 6.5 v4: 비가구에도 직립 적용

가구 외 객체에도 같은 로컬 +Y 정렬을 적용했다. 바닥 이동은 지정 가구에만 유지하고, 비가구는 root XYZ 위치를 보존했다. 120개 객체의 축 정렬, 가구 46개의 접지, 나머지 74개의 root 위치 보존을 확인했다.

대표 3개 장면·28개 객체를 같은 원본 추론 산출물에서 재처리했다. 이 단계에서는 전후 카메라를 동일하게 맞췄고, 정면·반대편 두 시점으로 총 12장의 비교 이미지를 남겼다.

| 가구만 직립 v3 | 전체 객체 직립 v4 |
|---|---|
| ![v3 상자형 객체](assets/all_object_upright/2a2d9c3e_before_front.png) | ![v4 상자형 객체](assets/all_object_upright/2a2d9c3e_after_front.png) |

이 장면에서는 `appliance_00`으로 분류된 상자형 객체의 축 각도가 약 157.77°에서 0°로 바뀌어 자세 변화가 뚜렷하다. 그러나 로컬 +Y를 기준으로 한 결과이므로 실제 물체의 올바른 위쪽을 알아냈다는 의미는 아니다. 거실의 TV·식물·책은 약 1~2도 수준의 작은 변화였고, TV의 부유와 책의 접촉 문제는 남았다.

근거: [v4 전체 객체 정렬 검증](ALL_OBJECT_UPRIGHT_VALIDATION.md).

## 7. 성과를 평가할 때 구분할 것

**실행 성공, 수치 규칙 충족, 시각적 품질은 서로 다른 결과다.**

| 표현하려는 성과 | 근거에 맞는 설명 | 피해야 할 해석 |
|---|---|---|
| 초기 원본 시점 보완 | 가시 영역 IoU와 미피복 픽셀 개선 | 완전한 3D 형상 정확도 99.1% |
| InSpace 대조 | 특정 공식 예제에서 camera 조건의 큰 영향 확인 | 자체 입력 실패 원인은 camera 하나 |
| SAM3D 자동화 | 자동 후보·마스크·메시·웹 확인을 연결 | 모든 모델 대비 보편적 품질 우위 |
| 지정 가구 접지 | 평가한 가구의 최저점과 기준 바닥 일치 | 모든 다리 접촉·소품 지지·충돌 해결 |
| 전체 객체 직립 | 로컬 +Y를 월드 +Y에 정렬 | 물체의 의미상 올바른 자세 복원 |
| 검증 PASS | 명시된 산출물·수치·브라우저 검사 통과 | 모든 입력에서 자연스러운 결과 |

기존 전체 샘플 생성 기록의 29개 입력 중 22개 PASS·7개 FAIL은 이전 보정 버전의 결과다. 7개 실패는 16MP 입력 제한에 따른 제출 실패였다. 최신 v4의 22개 장면 검증은 저장된 결과의 CPU 재처리이므로 같은 종류의 새 GPU 전체 생성 실험으로 합산하지 않는다. 자세한 조건은 [전체 샘플 기록](SAMPLES_BEFORE_AFTER_COMPARISON.md)에 있다.

## 9. 과거 기록 확인 방법

문서 작성 과정에서 사용자가 확인한 내용은 초기 목표, 형상·배치에 대한 불만, 파노라마 접근을 시도한 두 목적, 실제·생성 파노라마에서의 실패 경험, 초기 목표를 유지한 1차 마무리 범위다. 이들은 개발 의도와 경험의 근거이며, 자동 검사나 통제된 정량 실험을 대체하지 않는다.

현재 코드에서 제거된 문서도 Git 이력으로 읽을 수 있다. 다음 명령은 파일을 복원하거나 checkout을 변경하지 않는다.

```powershell
git show 3ed4b1d:README.md
git show 90eb0ac:README.md
git show 522b682:docs/living_room_validation.md
git show 0e213d5:docs/inspace_current_issues_2026-09-24.md
git show e7c4904:docs/sam3d_project_investigation.md
git show e7c4904:docs/sam3d_project_validation.md
```

과거 문서의 `output/`, `experiments/`, `/workspace/` 경로는 당시 환경의 산출물 위치다. 현재 저장소에 파일이 존재하거나 같은 명령으로 즉시 실행된다는 보장은 없다. 본문의 초기 수치와 관찰은 이 문서 기록에서 인용한 것이며, 현재 직접 다시 본 생성 결과와 구분한다.
